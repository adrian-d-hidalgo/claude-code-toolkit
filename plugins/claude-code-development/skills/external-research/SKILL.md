# external-research skill

Produces guidance on **when to leave the local repository** to consult external sources, **which sources to prioritise**, and **how to cite the evidence** so the reader can re-check. The output is the external findings interwoven into the calling agent's normal report — not a separate document.

This skill exists because the default reflex of "research" too often becomes "read more of the repo." Repository code answers what the repo does; it cannot answer whether the framework version has a known bug, what the upstream spec mandates, how other communities have solved the same problem, or what the changelog says about a recent regression.

## Methodology anchor

- **Triangulation** — confirm a claim against ≥2 independent authoritative sources before treating it as `[Verified-external]`. Single-source claims remain `[Inference]` from that source.
- **Source priority** — official docs > release notes / changelog > upstream issue tracker > RFC / spec > reputable comparative analyses > forum threads (last resort). See [`references/source-priority.md`](./references/source-priority.md).
- **Provenance over recency** — a 2-year-old RFC is more authoritative than a 2-week-old blog post. Recency matters for changelogs and known-issue lists; provenance matters for protocol behaviour.
- **Citation per the plugin-root evidence-rule** — see `${CLAUDE_PLUGIN_ROOT}/references/evidence-rule.md` for the four-level convention. External findings use `[Verified-external]` with URL + access date + version.

## When to leave the repo — the trigger checklist

Leave the repo when any of these holds:

- The error message is not generated by code in this repo (it comes from a library, runtime, or service).
- The behaviour of a library, framework, runtime, OS, or protocol needs to be confirmed.
- A version-specific question is asked ("does v14.2.3 still have this issue?").
- A spec, RFC, IETF standard, W3C standard, or vendor contract is the authority.
- A "is X a known issue?" question is asked — the answer lives in the upstream issue tracker, not the repo.
- A comparative decision is requested ("should we use A or B?") — comparable analyses live outside the repo.
- Industry practice is the unknown ("how do most teams solve Y?") — patterns live in books, talks, blogs, OSS examples.

If none of these hold and the question is "how does THIS code behave", stay in the repo.

## How to leave the repo — two paths only

### Path 1 — WebFetch (URL already known)

Use `WebFetch` when the URL is already in hand or trivially constructible:

- A changelog URL given by the user (`https://github.com/vercel/next.js/releases/tag/v14.2.3`).
- A specific issue (`https://github.com/<org>/<repo>/issues/<n>`).
- A spec / RFC (`https://www.rfc-editor.org/rfc/rfc9457`).
- An official docs page deep-linked to a section.

WebFetch is read-only and targeted. It does not browse, search, or follow link chains.

### Path 2 — Delegate to research-specialist sub-agent (open-ended search)

When the question requires **search across multiple sources**, **comparison**, or **discovering URLs that are not yet known**, do not call WebSearch from within this skill — the global rule reserves WebSearch for the `research-specialist` sub-agent. Surface a delegation request to the caller:

> Recommend research-specialist for: <one-sentence framing of the question>. Specifically need: <list of facts / comparisons / sources>. Quick mode is sufficient | Deep mode is recommended because <reason>.

The caller (main agent) is the integration point that invokes research-specialist. The skill does not invoke other agents directly.

## Workflow

1. **Confirm the leave-repo trigger.** If the question can be answered from the repo, do not leave. State why if the user asked to "investigate" something that lives locally.
2. **Decide path.** URL known → WebFetch. Search needed → recommend research-specialist with the framing above.
3. **Triangulate when possible.** A single source establishes `[Verified-external]` for direct quotes; behavioural claims about library/framework behaviour benefit from ≥2 sources.
4. **Apply source priority.** See [`references/source-priority.md`](./references/source-priority.md) for the priority order and rationale per source type.
5. **Cite every external claim** using `[Verified-external — URL accessed YYYY-MM-DD version X]`. Per the plugin-root `evidence-rule.md`.
6. **Reject fabricated APIs.** When external sources do not confirm a function, flag, option, or behaviour, do not assume it exists. Mark the claim `[Unverified — needs upstream confirmation]` and surface the gap.
7. **Self-check** before emission.

## Output integration

External findings interleave with the calling agent's normal report; they are not a separate document. Example shapes:

```markdown
**Finding [F-03]**: The Next.js app-router middleware is double-invoked under certain redirect conditions.
- Evidence: [Verified-external — https://github.com/vercel/next.js/issues/62018 accessed 2026-05-22; reproduced in CI run #1842 in this repo, src/middleware.ts:18 [Verified]]
- Impact: Auth state recomputed twice per redirect; minor latency, no correctness issue.
- Recommended action: Upgrade to 14.2.5+ which closes the issue per the changelog [Verified-external — https://github.com/vercel/next.js/releases/tag/v14.2.5 accessed 2026-05-22].
```

```markdown
**Recommendation**: Prefer Postgres logical replication over trigger-based CDC for this workload.
- Rationale: Lower write amplification (Postgres docs §31.1 [Verified-external]); avoids the trigger-recursion failure mode observed in upstream issue postgres/postgres#X [Verified-external]; aligns with the pattern documented in DDIA ch.11 [Verified-external — book pp. 451–456].
```

## Self-check (mandatory)

- [ ] Trigger justified — the question cannot be answered from the repo alone.
- [ ] Path correctly chosen — WebFetch only when URL known; research-specialist delegation when search is needed.
- [ ] Sources prioritised — official docs > changelog > issue tracker > spec > analysis > forum.
- [ ] Every external claim has `[Verified-external — URL accessed YYYY-MM-DD version]`.
- [ ] No fabricated APIs, flags, or options — if upstream does not confirm, mark `[Unverified]` and flag.
- [ ] Triangulation attempted where the claim is behavioural and a single source is thin.
- [ ] WebSearch was NOT used directly — only via research-specialist delegation.

## Scope and boundaries

This skill handles:

- The decision of when to leave the repo for external sources.
- The source-priority order and the citation format.
- WebFetch usage for targeted URL reads.
- Delegation framing for research-specialist.

This skill does not handle:

- Open-ended web search — reserved for research-specialist.
- Producing the final report — the calling agent owns the report; this skill produces the external findings that go into it.
- Code reading — that is `code-grounded-analysis` (transversal convention at plugin root).
- Choosing what to do with the findings — the calling agent's role decides (a bug fix is software-developer's; a design decision is software-architect's).

## Anti-patterns to reject

- **"Researching" by reading more repo code** when the question is about a library or spec — the answer is not in this repo.
- **Inventing flags, options, or function names** because they "sound right" for the library — fabrication is the dominant LLM failure mode here.
- **Citing an external claim without a URL or date** — the reader cannot re-check; the claim is unauditable.
- **Trusting a stale changelog** — confirm the version actually in use; "fixed in main" is not "fixed in your version."
- **Skipping triangulation when one source is a forum thread** — Stack Overflow and Reddit have a high outdated-information rate; require corroboration from official sources.
- **Invoking WebSearch from this skill** — global rule reserves WebSearch for research-specialist; this skill delegates instead.
- **Treating an LLM-generated summary as a source** — cite the underlying authoritative document, not the summary that paraphrased it.
- **Conflating "I read about this" with "the spec says this"** — quote the spec section directly.

## Communication

- Lead with **what was found and its source**, then the implication for the task.
- Tag every external claim with `[Verified-external — URL accessed YYYY-MM-DD]`. Tag local claims with their own evidence level per `evidence-rule.md`.
- When a single source is thin, say so — "single source; corroboration would strengthen this" is honest; pretending confidence is not.
- When delegating to research-specialist, frame the question precisely — open-ended "research X" wastes the delegation.
