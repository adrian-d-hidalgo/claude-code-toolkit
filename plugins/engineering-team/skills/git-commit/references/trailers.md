# Trailers (per-repo detection)

Trailers are structured `Key: Value` metadata appended after the commit body, parseable by `git interpret-trailers`. They decouple metadata from the subject line — issue references, sign-offs, reviewer attestations, and co-authorship don't bloat the prefix.

This skill **detects trailer conventions from the repo's recent history** and replicates them. It never imposes a trailer the repo isn't already using.

Spec reference: <https://git-scm.com/docs/git-interpret-trailers>.

## Trailer syntax

A trailer is a `Key: Value` line in the message footer, separated from the body by one blank line:

```
fix(payments): correct decimal handling in invoice totals

Replace floating-point arithmetic with Decimal across the totals
pipeline.

Signed-off-by: Real Person <real@example.com>
Refs: PAY-1342
Reviewed-by: Senior Engineer <senior@example.com>
```

Multiple trailers stack, one per line. Order within the footer follows the repo's convention (the skill detects which trailer appears first when there are several).

## Detection algorithm

When the skill starts work, it runs:

```
git log --no-merges -25 --pretty=format:"%h%n%s%n%b%n---"
```

For each trailer key the skill knows about, count how many of the 25 (or fewer) commits include that key in the footer. **If the trailer appears in ≥70% of the sampled commits, it is part of the repo's convention** and the skill must propose it in Option 2 or Option 3 (and Option 1 when the subject-only form is allowed to include footer-style references).

Below 70% but above 0% → optional; the skill mentions it in the detected-format header but does not force it into proposals.

0% → not part of the repo; never propose unless the user asks.

## Per-trailer guidance

### `Signed-off-by:`

Used for **Developer Certificate of Origin (DCO)** attestation. The committer certifies they have the right to submit the code under the project's license.

- Mandatory in 100% of Linux Foundation projects (Linux kernel, Kubernetes, cert-manager, OpenTelemetry, etc.).
- Common in open-source projects that require DCO via the DCO bot on GitHub.
- Format: `Signed-off-by: Full Name <email@example.com>`.
- Generated by `git commit -s`. The skill proposes it in text; the actual sign-off is the user's responsibility via `-s` or manual entry.

If detection shows ≥70% of the repo's commits include `Signed-off-by:`, every proposed message must end with the trailer using the user's git config name + email.

Source: <https://chaoss.community/kb/dco-setup/>.

### `Refs:` / `Reference:`

Lightweight reference to an issue or ticket **without** closing it. Used when a commit advances work on a ticket but doesn't fully resolve it.

- Common in repos that track work in Jira / Linear / Asana where commits don't auto-close (no GitHub keyword mapping).
- Format: `Refs: PROJ-1234` or `Refs: #45` or `Refs: org/repo#45`.

### `Closes #N` / `Fixes #N` / `Resolves #N`

GitHub and GitLab parse these keywords on merge to the default branch and **auto-close the linked issue**. Each keyword is interchangeable — use whichever the repo's log uses most.

- GitHub: `close/closes/closed`, `fix/fixes/fixed`, `resolve/resolves/resolved` followed by `#N` (same repo) or `org/repo#N` (cross-repo).
- GitLab: identical keyword set.
- **Only triggers** the auto-close when the commit ends up on the default branch. Pre-merge branches don't trigger it.

Source: <https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/using-keywords-in-issues-and-pull-requests>.

### `Reviewed-by:`

Reviewer attestation. Standard in Linux kernel and large open-source projects; rare in proprietary repos.

- Format: `Reviewed-by: Reviewer Name <email@example.com>`.
- Multiple `Reviewed-by:` lines are allowed (one per reviewer).
- The skill proposes it only when the repo's log uses it consistently and the user has named a reviewer.

### `Co-authored-by:` (human pair/mob programming)

GitHub and GitLab render `Co-authored-by:` trailers as additional commit authors in the UI, with proper attribution in contribution graphs.

- Format: `Co-authored-by: Pair Partner <pair@example.com>`.
- Multiple lines allowed (one per co-author).
- Use when the user mentions pair or mob programming with a named human collaborator.

**Never** use this trailer for AI attribution — see `non-goals.md` for the rationale. The blacklist explicitly excludes `Co-authored-by: Claude`, `Co-authored-by: GPT-*`, and any other AI co-author variant.

Source: <https://docs.github.com/en/pull-requests/committing-changes-to-your-project/creating-and-editing-commits/creating-a-commit-with-multiple-authors>.

## Composition with Conventional Commits

When a commit has both a `BREAKING CHANGE:` footer (from Conventional Commits) and trailers, the order is:

```
<subject>

<body>

BREAKING CHANGE: <description of the break>

Signed-off-by: ...
Refs: ...
Co-authored-by: ...
```

`BREAKING CHANGE:` comes first because it is part of the Conventional Commits envelope, not a metadata trailer. Other trailers follow in the order the repo's log uses most often.

## Hygiene

Linus Torvalds (Phoronix, 2025) publicly pushed back against `Link:` trailers in kernel commits that add no value — busywork metadata gets rejected. Apply the same rule here: **every trailer must do work for the reader**. If the repo uses `Reviewed-by:` ceremonially with no real review, the skill still replicates the convention (it's the repo's choice), but never invents trailers that don't earn their footer line.
